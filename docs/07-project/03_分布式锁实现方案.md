在 **Spring Boot** 中使用 **Redis 做分布式锁**，核心目标只有三点：**正确性、安全性、可维护性**。下面给你一套**工程级规范**，不是“能跑就行”的那种，而是**可长期用、可扩展、可审计**的方案。

------

## 一、分布式锁的基本原则（必须满足）

### 1️⃣ 互斥性（Mutual Exclusion）

同一时刻只有一个线程 / 实例能获得锁。

### 2️⃣ 锁必须有过期时间（TTL）

**禁止无过期时间的锁**，否则必然死锁。

### 3️⃣ 锁只能被持有者释放

不能出现「A 加锁，B 解锁」。

### 4️⃣ 加锁 & 设置过期时间必须原子

禁止 `SETNX` + `EXPIRE` 两步。

------

## 二、Redis 锁的标准实现方式（推荐）

### 🔐 1. 加锁（SET NX PX）

**规范写法：**

```
SET lock_key unique_value NX PX 30000
```

| 参数           | 说明                            |
| -------------- | ------------------------------- |
| `lock_key`     | 业务锁名                        |
| `unique_value` | **唯一标识（UUID + threadId）** |
| `NX`           | 不存在才设置                    |
| `PX`           | 毫秒过期时间                    |

👉 **Redis ≥ 2.6.12**

------

### Java 示例（Spring Boot）

```
String lockKey = "lock:order:" + orderId;
String lockValue = UUID.randomUUID().toString();
long expire = 30_000; // 30s

Boolean success = stringRedisTemplate.opsForValue()
    .setIfAbsent(lockKey, lockValue, expire, TimeUnit.MILLISECONDS);

if (!Boolean.TRUE.equals(success)) {
    throw new BizException("系统繁忙，请稍后重试");
}
```

------

## 三、解锁规范（必须用 Lua）

### ❌ 错误做法（禁止）

```
redisTemplate.delete(lockKey);
```

👉 可能删掉**别人的锁**

------

### ✅ 正确做法（Lua 脚本）

```
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

### Java 执行 Lua

```
DefaultRedisScript<Long> script = new DefaultRedisScript<>();
script.setScriptText(LUA_UNLOCK);
script.setResultType(Long.class);

redisTemplate.execute(
    script,
    Collections.singletonList(lockKey),
    lockValue
);
```

------

## 四、锁 Key 设计规范（非常重要）

### 命名规范

```
lock:{biz}:{resource}
```

示例：

```
lock:order:123456
lock:pay:user:10001
lock:stock:sku:888
```

👉 **禁止：**

```
orderLock
lock1
test_lock
```

------

## 五、锁的过期时间设计（经验值）

| 业务类型     | TTL            |
| ------------ | -------------- |
| 普通 DB 操作 | 5–10 秒        |
| 远程调用     | 15–30 秒       |
| 批处理       | 必须拆分或续期 |

> **原则**：
>  TTL ≥ 业务最大执行时间 × 2

------

## 六、锁续期（Watch Dog）规范（进阶）

### 什么时候需要？

- 不确定执行时间
- 有 IO / RPC / MQ

### 方案

- 后台线程定时 **PEXPIRE**
- 续期前校验 value 一致

⚠️ **自己实现复杂，推荐用 Redisson**

------

## 七、强烈推荐：Redisson（生产首选）

### Maven

```
<dependency>
  <groupId>org.redisson</groupId>
  <artifactId>redisson-spring-boot-starter</artifactId>
</dependency>
```

------

### 使用方式

```
RLock lock = redissonClient.getLock("lock:order:" + orderId);

boolean locked = lock.tryLock(0, 30, TimeUnit.SECONDS);
if (!locked) {
    throw new BizException("请勿重复提交");
}

try {
    // 业务逻辑
} finally {
    lock.unlock();
}
```

### Redisson 帮你解决了：

| 问题         | 是否解决 |
| ------------ | -------- |
| 原子加锁     | ✅        |
| 自动续期     | ✅        |
| Lua 解锁     | ✅        |
| 可重入       | ✅        |
| 崩溃自动释放 | ✅        |

👉 **企业级首选**

------

## 八、分布式锁使用禁区（血的教训）

❌ 锁里执行 HTTP 调用
❌ 锁里 sleep
❌ 锁粒度过大
❌ 一个锁包整个方法
❌ 锁时间拍脑袋

------

## 九、什么时候「不该」用 Redis 锁

| 场景       | 更优方案                         |
| ---------- | -------------------------------- |
| 单 JVM     | `synchronized` / `ReentrantLock` |
| 数据唯一性 | 数据库唯一索引                   |
| 严格顺序   | MQ                               |
| 高一致性   | DB 行锁                          |

------

## 十、推荐封装方式（工程规范）

```
public interface DistributedLock {

    boolean tryLock(String key, String value, long ttl);

    void unlock(String key, String value);
}
```

统一封装，**禁止业务直接操作 Redis**。
